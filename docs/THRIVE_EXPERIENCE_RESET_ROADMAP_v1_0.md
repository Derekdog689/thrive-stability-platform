# THRIVE Experience Reset Roadmap v1.0

Date: 2026-09-30
Status: approved roadmap direction; implementation not yet authorized
Owner: DSS Enterprises
Scope: participant experience, visual system, Story, Resources, Recovery Support proving ground, follow-up, and engagement
Production impact: none
Database impact: none at this gate
Trust Engine impact: none

## North star

THRIVE is not primarily a tracker.

THRIVE is a **responsive support environment**.

A tracker records.
A responsive support environment:

- notices;
- interprets;
- brings something useful;
- helps the participant act;
- remembers what happened;
- follows up;
- adapts;
- shows progress;
- carries the story forward.

The participant experience should feel:

> Calm enough to trust, alive enough to return to, direct enough to help.

## Core experience contract

Current tendency:

input -> summary -> card

Target experience:

input -> understand -> useful return -> concrete action -> real resource -> follow-up -> adaptation -> visible progress -> Story

THRIVE should do more of the cognitive lifting while the participant keeps control.

## Five experience pillars

### 1. Value

Every meaningful participant input should return something useful.

A return should do at least one of the following:

- reveal something useful;
- offer a concrete action;
- bring a real resource;
- help make a decision;
- connect earlier context to the current moment;
- follow up on something previously tried.

### 2. Direction

THRIVE should translate reflection into understandable choices.

Example:

Instead of only:
"Routine and confidence may be connected."

THRIVE may offer:
"What would help most right now?"

- sleep;
- morning routine;
- meeting/support;
- one task;
- something else.

The participant keeps the decision.

### 3. Resources

THRIVE should bring useful resources to the participant rather than merely tell them to go look for help.

Resource quality standard:

- what is this;
- why would I use it;
- what do I need;
- where do I go;
- what happens next.

### 4. Story

Story is the accumulation layer.

Story should answer:

- what happened;
- what changed;
- what was completed;
- what keeps coming back;
- what remains unfinished;
- what carries forward.

Story should preserve source-lane ownership while making the participant's recent activity understandable as one continuing experience.

### 5. Visual life

The interface should visibly react to meaningful participant state.

The participant should be able to feel that something changed before reading a paragraph explaining it.

Visual life includes:

- atmosphere;
- motion;
- progress geography;
- completion artifacts;
- partial-completion states;
- lane identity;
- environmental illustration;
- layered depth;
- visual surprise;
- responsive identity;
- negative space;
- typography as emotion.

## Cross-cutting follow-up

Follow-up sits under every pillar.

THRIVE should remember:

- what was offered;
- what was chosen;
- what was attempted;
- what helped;
- what did not;
- what should change next.

The product should not repeat the same generic suggestion when the participant has already shown that it was not useful.

## Audience assumption

THRIVE should not be designed only for a participant with strong self-awareness, high bandwidth, or strong system-navigation skills.

The participant may:

- have limited bandwidth;
- not know which systems or resources exist;
- feel uncertain about what to do next;
- have difficulty converting reflection into action;
- need more structure on some days than others.

THRIVE should reduce that burden without removing participant agency.

## Adult tone

THRIVE may be direct when the facts support it.

Example:

"You planned to do this three times and did it once."

Then:

- try again;
- make it smaller;
- change the approach;
- leave it here.

No shame.
No fake cheerleading.
No clinical invention.
No failure theater.

## Visual direction

### Working visual direction: Living Signal

Living Signal is not one fixed palette or one design trend.

It combines:

1. atmosphere;
2. signal;
3. motion;
4. accumulation.

The current green/white card stack should evolve into a richer visual system with stronger hierarchy and more obvious visual consequences.

### Visual reference ingredients

The following are inspiration ingredients, not approved themes:

- deep restorative tones such as stormy teal / charcoal;
- light fresh-start tones such as parchment / soft cream;
- modern twilight tones such as navy / lilac / indigo;
- warm amber or sunset milestone accents;
- soft glass or translucent layering;
- subtle grain or linen texture;
- soft low-opacity elevation shadows;
- organic curves;
- stronger depth;
- environmental imagery;
- responsive daypart atmosphere.

No single style named during exploration is itself the approved THRIVE identity.

### Time-based atmosphere

Time-based visual shifts may be explored:

- morning: brighter, clearer;
- afternoon: balanced, focused;
- evening: deeper, quieter.

Time-of-day atmosphere must not be confused with inferred emotional state.

### Motion grammar

Motion should mean something.

Candidate states:

- arrive;
- advance;
- resolve;
- carry;
- open;
- acknowledge.

Avoid:

- constant animation;
- confetti for routine actions;
- flashing failure states;
- punitive shake effects;
- motion without meaning.

### Cumulative progress

Avoid brittle streak mechanics as the default.

Prefer cumulative growth language such as:

- "You checked in 18 times this month."
- "You came back after two days away."
- "You completed 4 actions this week."
- "You resumed this Goal after pausing it."

Progress should accumulate without making one missed day erase prior effort.

### Completion artifacts

Meaningful completion should leave a visible artifact.

Examples:

Goal:
- title;
- completion date;
- what was practiced or achieved;
- optional build-on decision.

Money:
- cycle closed;
- available / planned / used;
- one or two grounded takeaways.

Wellness:
- cumulative participation rhythm;
- meaningful change across time.

Support:
- active/resolved thread;
- participant-confirmed action or resource use.

## Story visual architecture

Story should not look like an ordinary card feed.

Candidate structure:

### Today / this week ribbon

A timeline or progress geography showing:

- Wellness check-ins;
- Goal movement;
- Goal completion;
- Money cycle close;
- Support requests;
- Support replies;
- resources saved;
- participant-confirmed follow-through.

### Chapter

A larger visual surface summarizing what the period added up to.

### Carry forward

One or two unresolved or next-step threads.

Story should become visually fuller when real activity accumulates.

## Resource architecture

Resources should grow beyond the current limited set.

### Layer A: live verified resources

Examples:

- meeting finders;
- community resources;
- current support directories;
- current public-benefit destinations.

### Layer B: curated THRIVE library

Examples:

- DSS-approved links;
- recovery literature references;
- worksheets;
- financial education;
- employment resources;
- transportation resources;
- housing resources;
- education resources.

### Layer C: participant-saved resources

Items the participant chooses to keep.

### Layer D: guided pathways

THRIVE should not become a link farm.

Examples:

Food support:
eligibility -> apply -> gather proof -> follow up.

Recovery support:
find meeting -> save one -> attend if chosen -> tell THRIVE whether it helped -> adapt.

### Current resource lesson

Current Social Security and SNAP resources are useful because they land the participant close to the real destination.

211 remains useful but can be confusing and inconsistent.

Future resource design should favor:

- direct destinations;
- clear next steps;
- source context;
- alternate path;
- participant-friendly explanation.

## Recovery Support proving ground

Recovery Support is the first proving ground because live use has repeatedly requested:

- meetings;
- literature;
- recovery-oriented resources;
- more than one person to lean on;
- practical feedback;
- direction beyond generic Support routing.

### Four concrete paths

#### Find something

Meeting / resource.

THRIVE should return real source-grounded options rather than say "find a meeting."

#### Read something

Recovery literature, educational material, or other approved reading.

THRIVE should provide source, context, and a useful preview or summary within copyright limits.

#### Connect with someone

Help the participant expand their support circle without inventing contacts.

#### Build something

Help the participant build a participant-chosen recovery routine.

### Follow-up

Follow-up should reference the actual action.

Examples:

- Were you able to make it to the meeting you saved?
- Did you read the item you saved?
- Did you contact anyone?
- Did the routine work for you?

If the answer is no or not useful, THRIVE should change direction.

### Progress and Story

Only participant-confirmed activity should become completion evidence.

Examples:

- meeting saved;
- meeting attended, participant-confirmed;
- reading tried;
- new support connection, participant-confirmed;
- routine tried;
- different approach chosen.

No sobriety score.
No recovery-performance ranking.

## Support continuity

When the participant returns to Support with the same explicit context while a related Support thread is still open:

- show the existing thread first;
- make continuation easy;
- allow a separate request if the participant truly wants a different issue.

Do not automatically merge, delete, or rewrite historical Support records.

## What remains from the current UI

Likely keep or evolve:

- mobile-first layout;
- bottom navigation concept;
- participant greeting;
- clear large-touch targets;
- rounded geometry;
- lane icons;
- restrained translucency;
- readable typography;
- accessibility intent;
- core participant flows;
- current database model;
- Wellness logic;
- Goals ownership;
- Money logic;
- Support persistence;
- cross-lane synthesis.

## What should be reconsidered

- dominant emerald palette;
- repeated white/green card rhythm;
- oversized raw Goal titles on Today;
- equal visual weight across routine and meaningful states;
- completion disappearing too quickly;
- generic "Open Support" as the end of intelligence;
- reflective prompts with nowhere to answer;
- generic encouragement that does not change the next step;
- institutional-feeling surfaces.

## Roadmap

### Phase 1: single source of truth

This roadmap becomes the master experience direction.

Existing v0.1 reset, visual-direction, and recovery-proving-ground documents remain historical design evidence.

### Phase 2: visual direction board

Create review-only mockups for:

1. Today after an ordinary check-in;
2. Today after meaningful completion;
3. Story week view;
4. Goal completion;
5. Money closeout;
6. Recovery Support resource flow;
7. partial completion;
8. no active Goals / no active Money plan while Story remains meaningful.

The editorial-layout idea should be explored visually where it adds value, especially Story, milestone moments, and Money closeout. It is not a global layout rule.

### Phase 3: Recovery Support proving ground

Prove one complete loop:

need -> understand -> real resource -> participant action -> follow-up -> adaptation -> visible progress -> Story

Do not spread the pattern across all lanes until this loop proves useful and alive.

### Phase 4: Story layer

Build Story as the accumulation surface across:

- Wellness;
- Goals;
- Money;
- Support;
- participant-confirmed resource actions.

### Phase 5: visual system rollout

Apply the approved visual system across:

- Today;
- Wellness;
- Goals;
- Money;
- Support;
- Resources;
- Story.

### Phase 6: resource expansion

Grow Resources into a guided, source-grounded subsystem.

### Phase 7: follow-up and adaptation

Make the product remember what was tried and change the next return.

### Phase 8: production hardening

After experience validation:

- reconcile live schema;
- identify minimum required writes;
- verify mobile;
- verify accessibility;
- verify motion/performance;
- validate resource sources;
- test edge cases;
- use preview deployment;
- phone-test production candidate;
- merge only after approval under the established workflow.
