"Old THRIVE with some Living Signal influence" is not acceptable.

## Frozen visual benchmark

The approved board defines the expected universe.

Key states:

1. TODAY — Morning / Fresh Start
2. TODAY — Evening / Sanctuary
3. GOAL COMPLETION
4. MONEY CLOSEOUT
5. STORY — Week View
6. RECOVERY SUPPORT
7. MEETING RESULTS

Supporting visual principles:

- environmental illustration is structural, not decorative wallpaper;
- scenery contributes to emotional atmosphere;
- each lane has distinct visual identity;
- morning and evening visibly differ while remaining the same app;
- cards support the environment rather than dominate it;
- visual hierarchy distinguishes routine from meaningful moments;
- completion feels like an event;
- progress geography shows accumulation;
- Story looks like movement, not a report;
- Resources look actionable;
- typography carries hierarchy and emotion;
- layered depth replaces flat institutional card stacks;
- lane accents are distinct;
- no dominant hospital-green visual system;
- no generic white-card wall;
- no childish trophies;
- no failure theater;
- no "close enough" interpretation of the board.

## Product principle

THRIVE is not primarily a tracker.

Target participant experience:

-> understand
-> useful return
-> concrete action
-> real resource
-> follow-up
-> adaptation

The visual system is part of that contract.

## Preservation rule

The Experience Reset is **not** a backend rewrite.

Preserve:

- current database;
- participant history;
- Wellness writes;
- Goals lifecycle;
- Money logic;
- Support lifecycle;
- Resources governance;
- cross-lane truth;
- auth;
- existing source ownership;
- Trust Engine boundary.

The reset should be treated as:

**keep the engine, replace the participant-facing presentation layer**

## Safe migration strategy

Do not replace the production shell all at once.

Build the Living Signal presentation beside the existing shell.

Recommended candidate routes:

- /today-living
- /wellness-living
- /recovery-support
- /resources-living
- /story-candidate

These candidate routes may read current THRIVE data while leaving production routes intact.

Only migrate a production route after:

1. visual acceptance against the board;
2. Android phone test;
3. functional parity confirmation;
4. accessibility review;
5. explicit approval.

## Acceptance standard

A future candidate passes only if the participant can open it and immediately recognize:

**this is the app from the board**

Not:

- "I can see the influence"
- "the background changed"
- "the colors are better"
- "it is closer"

The target is same visual universe, same product identity, same emotional quality.
